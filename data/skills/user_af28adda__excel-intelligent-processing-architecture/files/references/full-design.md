## 一、方案概述

本方案面向标准表、轻度非标表、可标准化复杂 Excel 表，以及多表关联分析场景。目标用户为无 SQL 基础的普通用户，核心体验是：用户上传文件并描述需求，系统自动完成结构探测、标准化、入仓、脚本生成、脚本执行、自然语言解读和结果输出。

调整后的核心原则是：

- 默认自动处理，但对高歧义口径进行轻量确认；
- 复杂 Excel 不直接判死刑，优先尝试标准化；
- SQL、清洗、字段映射、重试和降级过程对用户默认隐藏，但系统内部可审计；
- 明确支持多文件多表关联，以及单个 Excel 文件内多 Sheet 之间的关联分析；
- 大模型只负责理解意图、生成分析计划、辅助 SQL/脚本和解释结果，不直接承担大规模数据读取与精确计算；
- 正式分析默认先落地可执行脚本，再用该脚本产生首次验证结果，脚本本身即为可复用 Recipe。

核心链路：

```text
文件上传
  -> 轻扫分级
  -> 标准化/清洗
  -> 多表关系识别
  -> DuckDB 入仓
  -> 数据画像 SQL
  -> 业务歧义确认
  -> 生成可执行分析脚本
  -> 用脚本执行首次正式分析
  -> 脚本结果验证
  -> 自然语言解读
  -> 脚本作为 Recipe 留存
  -> 重试与降级
```

## 二、标准表定义

标准表是指满足以下条件的规整二维表：

- 首行为单一表头；
- 每列字段名唯一且非空；
- 每行表示一条记录；
- 每列表示一个字段；
- 无合并单元格；
- 数据行连续；
- 无空行空列穿插；
- 无标题行、备注行、汇总行混入明细数据；
- 日期、数值、百分比、货币等字段类型可稳定解析。

标准表可以直接注册入 DuckDB 进行分析。

## 三、非标分级策略

原方案中将合并单元格和多级表头直接划为不可修复，过于保守。调整后采用四级分类。

| 级别 | 类型 | 典型场景 | 处理方式 |
| --- | --- | --- | --- |
| A1 | 可标准化复杂非标 | 合并单元格、多级表头、标题区、分组表头、纵向分类合并 | 自动生成标准化计划，转为标准表后继续 |
| A2 | 不可可靠修复非标 | 一个 Sheet 内多张交错表、单元格内嵌多条记录、字段语义严重缺失、结构无法稳定推断 | 终止自动分析，给出问题定位和修改建议 |
| B | 轻度非标 | 表头不在第一行、尾部汇总行、末尾空行空列、少量格式不统一 | 自动清洗修正，用户默认无感知 |
| C | 标准表 | 完全符合标准表定义 | 直接注册入 DuckDB |

### A1 可标准化复杂非标处理

A1 不再直接退出，而是进入标准化层：

- 纵向合并单元格：将分类值向下填充；
- 横向合并单元格：将分组表头向右传播；
- 多级表头：合并为单行字段名；
- 标题区、说明区：从数据区剥离；
- 汇总行：识别后移出明细数据；
- 原始 Sheet 名、原始行号、原始列号可作为溯源字段保留。

当系统无法唯一判断表头、数据区或合并语义时，进入轻确认，而不是盲目处理。

## 四、轻扫分级层

轻扫分级的目标是判断结构，不做正式分析。轻扫应尽量轻量，但不承诺毫秒级完成。对于常规文件应控制在秒级以内；对于大文件或复杂 Excel，可进入异步或进度提示。

### 采样策略

默认采样：

- 首部 50 行；
- 尾部 5 行；
- 合并单元格范围；
- Sheet 维度信息；
- 非空单元格密度；
- 候选表头行；
- 对超宽表可提升至 100 行。

自适应扩展：

- 如果前 50 行无法识别表头，继续扫描到配置上限；
- 如果检测到多个非空区域，进入多表区域识别；
- 如果 Sheet 数量大于 1，进入多 Sheet 关系探测；
- 如果尾部存在多个汇总区，记录为风险项。

### 分级输出

```python
{
    "level": "A1" | "A2" | "B" | "C",
    "issues": [
        {"type": "multi_row_header", "detail": "检测到第2-3行为多级表头"}
    ],
    "sheets": [
        {"name": "订单", "rows": 10001, "cols": 12, "candidate_header_row": 1}
    ],
    "merged_ranges": ["A2:A10", "B1:D1"],
    "estimated_rows": 50000,
    "raw_columns": ["订单编号", "product_name", "金额"]
}
```

## 五、标准化与清洗层

### 处理原则

标准化与清洗层负责把人类可读的 Excel 格式转换为机器可分析的标准表。该层必须由脚本执行，不能让 LLM 根据未清洗内容直接推断结果。

处理完成后输出：

- 标准化 DataFrame；
- 字段映射；
- 清洗日志；
- 数据质量报告；
- 原始到标准表的溯源关系。

### 字段名策略

采用三层字段名：

| 字段 | 说明 |
| --- | --- |
| `raw_name` | 原始字段名，保留用户文件中的真实表头 |
| `safe_name` | SQL 安全字段名，用于 DuckDB 查询 |
| `semantic_name` | 语义名称，用于解释字段含义和展示 |

示例：

```python
{
    "raw_name": "实收金额（元）",
    "safe_name": "actual_amount_yuan",
    "semantic_name": "实收金额"
}
```

SQL 中使用 `safe_name`，展示给用户时使用 `raw_name` 或 `semantic_name`。

### 清洗日志

清洗日志默认不打扰用户，但必须保留：

```python
{
    "fixes": [
        {"type": "fill_merged_cells", "ranges": 12, "detail": "填充纵向合并单元格"},
        {"type": "flatten_header", "rows": [1, 2], "detail": "多级表头合并为单行字段名"},
        {"type": "remove_summary", "rows_removed": 1, "detail": "移除尾部合计行"}
    ],
    "before": {"rows": 1005, "cols": 12},
    "after": {"rows": 1001, "cols": 11}
}
```

当用户追问“做了什么处理”时，系统应能用自然语言解释。

## 六、多表与多 Sheet 关联支持

本方案明确支持以下关联场景：

1. 多个独立文件之间的表关联；
2. 单个 Excel 文件中多个 Sheet 之间的关联；
3. 单个 Sheet 中多个可识别表区域之间的关联；
4. 标准表与清洗后标准表之间的关联；
5. 用户自然语言指定的关联分析，例如“订单表关联客户表，统计各地区销售额”。

### 多 Sheet 入仓策略

对于单个 Excel 文件：

- 每个 Sheet 独立轻扫；
- 每个 Sheet 独立分级；
- 每个可分析 Sheet 标准化为一张表；
- 表名采用 `workbook_name__sheet_name` 或用户友好别名；
- 保留 `source_file`、`source_sheet`、`source_row` 等溯源字段。

示例：

```text
销售数据.xlsx
  - 订单明细 -> sales_data__orders
  - 客户信息 -> sales_data__customers
  - 产品信息 -> sales_data__products
```

### 多表关系识别

系统在入仓前后生成关系画像：

- 字段名相似度；
- 字段值重叠率；
- 主键候选识别；
- 外键候选识别；
- 字段唯一性；
- 缺失率；
- 类型兼容性；
- 表规模和基数。

候选关系示例：

```python
{
    "relations": [
        {
            "left_table": "orders",
            "left_key": "customer_id",
            "right_table": "customers",
            "right_key": "customer_id",
            "confidence": 0.98,
            "evidence": {
                "name_similarity": 1.0,
                "value_overlap": 0.97,
                "right_unique_rate": 1.0
            }
        }
    ]
}
```

### 关联确认策略

对于高置信关系，系统可自动使用。

对于低置信或多候选关系，应轻量确认：

```text
我发现“订单明细”和“客户信息”可能可以通过“客户ID”关联。
是否使用这个关系来分析？
```

如果用户需求已经明确指定关联字段，则优先使用用户指定字段。

### 多表 SQL 生成规则

多表 SQL 必须遵守：

- 只使用已注册表；
- Join 字段必须来自关系画像或用户明确指定；
- 禁止无约束笛卡尔积；
- 多对多关系必须先提示风险或进行去重策略；
- Join 后行数异常膨胀时触发验证；
- 结果字段必须回译为用户可读名称。

示例：

```sql
SELECT
    c.region AS region,
    SUM(o.amount) AS total_amount
FROM orders o
JOIN customers c
  ON o.customer_id = c.customer_id
WHERE o.amount IS NOT NULL
GROUP BY c.region
ORDER BY total_amount DESC
LIMIT 100;
```

### Join 结果验证

关联分析必须记录：

- Join 前左右表行数；
- Join 后行数；
- 未匹配左表行数；
- 未匹配右表行数；
- Join 膨胀倍数；
- 是否存在重复键；
- 是否可能发生重复计数。

当 Join 后行数异常膨胀时，系统应停止输出结论，先提示风险。

## 七、DuckDB 注册与数据画像

标准化后的单表或多表统一注册入 DuckDB。

### 注册流程

1. 创建会话级 DuckDB 实例；
2. 将每个标准表注册为独立 DuckDB 表；
3. 校准字段类型；
4. 生成表结构摘要；
5. 生成数据画像；
6. 生成关系画像；
7. 验证行数一致。

### 数据画像内容

数据画像包括：

- 总行数；
- 字段名和字段类型；
- 空值率；
- 唯一值数量；
- 数值字段均值、中位数、最小值、最大值；
- 日期字段范围；
- 文本字段 Top 值；
- 主键候选；
- 外键候选；
- 表间候选关系。

数据画像由 SQL 或脚本生成，传给 LLM 的是摘要，不是原始大表。

## 八、两层 SQL 驱动

### 第一层：洞察 SQL

洞察 SQL 用于生成数据画像和关系画像，完全自动执行。

典型查询：

- 行数；
- 空值统计；
- 字段基数；
- 日期范围；
- 数值分布；
- 主键候选；
- 外键候选；
- 表间字段重叠率。

### 第二层：执行 SQL

执行 SQL 用于回答用户问题。Agent 可生成 SQL，但必须执行和验证。

SQL 生成上下文包括：

- 用户原始需求；
- 表结构；
- 字段映射；
- 数据画像；
- 关系画像；
- 可用表列表；
- 清洗日志摘要；
- 结果行数上限；
- 安全规则。

### SQL 自动化边界

默认不把 SQL 暴露给用户，但在以下情况应进行自然语言确认：

- 指标口径不明确，如“增长率”“活跃”“复购”；
- 多个字段都可能满足用户意图；
- 多表关联字段存在多个候选；
- Join 关系可能造成重复计数；
- 用户需求会产生大规模明细结果。

确认时不展示 SQL，只确认业务含义。

## 九、SQL 安全与约束

SQL 执行应使用只读沙箱。

允许：

- `SELECT`;
- `WITH`;
- `JOIN`;
- `GROUP BY`;
- `HAVING`;
- `ORDER BY`;
- `LIMIT`;
- 窗口函数；
- 安全的类型转换。

禁止：

- `INSERT`;
- `UPDATE`;
- `DELETE`;
- `DROP`;
- `ALTER`;
- 文件系统读写；
- 外部网络访问；
- 未约束笛卡尔积。

关于全表扫描：

- 允许聚合型全表扫描，例如 `COUNT`、`SUM`、`GROUP BY`；
- 禁止无聚合的大规模明细全表输出；
- 明细查询必须自动加 `LIMIT`；
- 超大表应优先按用户需求增加过滤条件。

## 十、结果验证与解读层

### 结果验证

输出前至少验证：

- SQL 是否成功执行；
- 结果是否为空；
- 结果行数是否超限；
- 聚合结果是否可能重复计数；
- Join 后行数是否异常膨胀；
- 数值字段是否存在异常极值；
- 日期范围是否符合用户问题；
- 字段回译是否准确。

### 解读层

解读层负责把结果转换为普通用户可理解的语言。

解读规则：

- 只基于已执行结果，不编造额外结论；
- 明确说明数据范围；
- 对空值、过滤、Join 未匹配、截断等问题给出提示；
- 对高风险结论使用保守表述；
- 同时输出结构化结果表。

示例：

```text
按客户地区关联订单明细和客户信息后，共匹配 9,862 条订单，占订单总数 98.6%。
华东地区销售额最高，为 128.5 万，占已匹配订单销售额的 35.2%。
另有 139 条订单未匹配到客户信息，未计入地区统计。
```

## 十一、脚本优先的模板沉淀层（Recipe）

模板沉淀保留，但需要从“字符串替换 SQL”和“事后导出脚本”升级为“脚本优先的执行载体”。

核心规则：

- 正式分析型任务默认落地脚本；
- 脚本在数据结构洞察、标准化计划、关系画像和必要业务歧义确认之后生成；
- 首次正式结果必须由该脚本执行产生；
- 脚本执行成功且结果通过验证后，该脚本即成为可复用 Recipe；
- 探索性分析可使用临时代码或临时 SQL，但不能把临时执行结果作为最终正式结果；
- 纯结构检查、不可恢复结构诊断、用户明确不要复用的一次性极小查询，可以不落地脚本。

这种设计让“首次分析逻辑”和“复用逻辑”保持同源，避免先用一套临时 SQL 得出结果、再从结果反推脚本时发生逻辑漂移。

### 模板内容

Recipe 由两层组成：

1. 可执行脚本，用于首次执行和后续复用；
2. 结构化 Recipe 元数据，用于审计、再生成脚本和跨文件匹配。

Recipe 元数据应包含：

- 用户意图；
- 表角色；
- 字段角色；
- 关联关系；
- 指标口径；
- SQL AST 或结构化查询计划；
- 展示字段；
- 解读类型；
- 适用条件；
- 脚本入口和参数；
- 原始 SQL，仅作为调试信息。

示例：

```python
{
    "recipe_name": "按客户地区统计销售额",
    "intent": "关联订单表和客户表，统计各地区销售额",
    "table_roles": {
        "fact_table": {"role": "订单明细表", "required": True},
        "dim_table": {"role": "客户信息表", "required": True}
    },
    "field_roles": {
        "join_key": {"role": "客户ID", "required": True},
        "dimension": {"role": "地区", "required": True},
        "metric": {"role": "销售金额", "required": True}
    },
    "join_plan": [
        {"left": "fact_table.join_key", "right": "dim_table.join_key", "type": "inner"}
    ],
    "aggregation": {
        "group_by": ["dimension"],
        "metrics": [{"field": "metric", "agg": "sum", "alias": "销售额"}]
    }
}
```

### 脚本生成时机

脚本必须在以下条件满足后生成：

1. 已完成文件、Sheet、表区域和候选表头识别；
2. 已完成标准化计划，合并单元格、多级表头、标题行、汇总行等处理方式明确；
3. 已完成字段映射，至少包含原始名、SQL 安全名和展示名；
4. 多表场景下已完成关系画像，或用户已确认 Join 字段；
5. 指标口径、时间口径、过滤条件和输出格式没有阻塞性歧义；
6. 已确定结果行数上限和 SQL/脚本安全约束。

脚本生成后，系统应直接执行该脚本来产生首次正式结果。脚本执行失败时，应修复脚本并重跑，而不是绕过脚本改用临时 SQL 交付结果。

### 脚本交付要求

脚本至少满足：

- 接受一个或多个输入文件路径参数；
- 接受可选 sheet、输出目录、输出格式参数；
- 内含读取、标准化、字段映射、Join、分析、验证、输出步骤；
- 默认无隐藏交互，适合第三方调度；
- 成功时退出码为 `0`，失败时为非零；
- 失败信息写入 stderr，便于调度平台捕获；
- 输出 CSV、JSON、XLSX 或 Markdown 等明确产物；
- 保存清洗日志、生成 SQL、关系假设、验证结果和截断信息。

推荐命令形态：

```text
python analyze_sales_by_region.py --input sales.xlsx --output-dir runs/sales_region
```

脚本不能只是临时代码片段。它应具备 ETL 作业的基本品质：可参数化、可重跑、可审计、可失败定位、可由调度平台调用。

### 模板复用

模板复用时：

1. 新文件轻扫；
2. Sheet 或表区域标准化；
3. 识别表角色和字段角色；
4. 匹配 Join 关系；
5. 验证必需角色是否齐全；
6. 复用原脚本，或根据结构化 Recipe 重新生成脚本；
7. 执行脚本并验证；
8. 输出解读和运行产物。

如果角色匹配有歧义，应让用户选择业务字段，而不是展示技术字段。

## 十二、脚本质量与 ETL 标准

正式分析脚本应按 ETL 作业标准生成。目标不是把所有逻辑写得复杂，而是保证脚本可以被重复执行、调度和排障。

### 结构要求

推荐脚本结构：

```text
parse_args()
setup_run_dir()
extract_inputs()
profile_sources()
transform_to_standard_tables()
validate_standard_tables()
analyze()
validate_results()
write_outputs()
write_run_manifest()
main()
```

对于简单任务，可以合并函数，但仍应保留 Extract、Transform、Validate、Output 的清晰边界。

### 参数化要求

脚本必须通过 CLI 参数接收运行时输入，不应硬编码用户本机路径或业务日期。

建议参数：

| 参数 | 说明 |
| --- | --- |
| `--input` 或 `--inputs` | 一个或多个 Excel/CSV 文件路径 |
| `--sheet` | 可选，指定 Sheet |
| `--output-dir` | 运行目录 |
| `--output-format` | CSV、JSON、XLSX、Markdown 等 |
| `--as-of-date` | 可选，业务日期或报表日期 |
| `--max-result-rows` | 明细输出上限 |
| `--strict` | 开启严格校验，校验失败直接非零退出 |

### Extract 标准

Extract 阶段负责读取和源数据画像：

- 不修改源文件；
- 记录输入文件路径、大小、修改时间、sheet 列表和读取引擎；
- CSV 读取前处理编码、分隔符、表头和换行符推断；
- Excel 读取前记录合并单元格、隐藏行列、公式、候选表头和维度信息；
- 大文件避免一次性输出原始明细到日志。

### Transform 标准

Transform 阶段负责把人类格式转为标准表：

- 标准化步骤必须确定且可重复；
- 字段命名保留 `raw_name`、`safe_name`、`semantic_name` 映射；
- 记录删除的标题行、空行、汇总行、备注行和异常行；
- 合并单元格填充、多级表头展开、类型转换必须写入清洗日志；
- 不在 Transform 阶段做业务结论解释。

### Validate 标准

Validate 阶段必须覆盖输入、转换、分析结果三个层级。

输入校验：

- 必需文件存在且可读取；
- 必需 Sheet 或表区域存在；
- 必需字段或字段角色可匹配。

转换校验：

- 标准化后列名唯一且非空；
- 行数变化可解释；
- 关键字段空值率在可接受范围内；
- 类型转换失败数量可解释。

分析校验：

- SQL 或 dataframe 逻辑成功执行；
- 聚合结果未因 Join 发生重复计数；
- Join 前后行数、未匹配数和膨胀倍数被记录；
- 空结果、异常极值、截断输出被明确记录；
- 结果行数不超过输出上限。

校验结果应写入机器可读文件，例如 `validation.json`。

### Load/Output 标准

输出阶段负责生成用户和系统都能消费的产物：

- 结果表保存为 CSV/XLSX/JSON 中至少一种；
- 自然语言摘要保存为 Markdown 或 JSON 字段；
- 字段映射、清洗日志、SQL、校验结果、运行清单分别保存；
- 输出文件名稳定，便于调度平台和下游系统读取；
- 覆盖已有输出前应使用明确的输出目录，避免写入源文件目录造成混乱。

### 可观测性与失败策略

脚本应输出：

- stdout：简洁进度和最终产物路径；
- stderr：错误原因和修复建议；
- 日志文件：完整运行过程；
- 退出码：成功为 `0`，失败为非零。

失败应尽早暴露。缺少必需字段、Join 歧义、校验失败、结果可能重复计数时，不应静默输出看似成功的结果。

### 依赖与可移植性

优先使用当前环境已存在或容易安装的依赖。可选依赖必须检测后再使用：

- `openpyxl`、`pandas`、`duckdb` 可作为默认组合；
- `polars`、`sqlglot`、`chardet` 等作为可选增强；
- 缺少可选依赖时应降级或给出清晰错误，不应生成必然无法运行的脚本。

## 十三、重试与降级

### 重试策略

可恢复错误可以重试：

- 临时 IO 异常；
- 编码识别失败；
- 类型推断失败；
- SQL 语法错误；
- 字段引用错误；
- 查询超时。

SQL 自修复最多 2 次。修复失败后，用自然语言提示用户换一种描述，或说明缺少字段。

### 降级策略

降级需要区分不同失败原因：

| 失败类型 | 降级方式 |
| --- | --- |
| DuckDB 注册失败 | pandas/polars 读取并处理 |
| DuckDB SQL 语法失败 | Agent 修复或 sqlglot 转换 |
| DuckDB 资源不足 | 分块读取、过滤、采样或 polars |
| SQL 无法表达 | pandas/polars API 实现 |
| 文件结构不可识别 | 输出结构问题报告 |

不建议把“Pandas 降级”仍然建立在 `duckdb.query(df)` 上，否则底层仍依赖 DuckDB。

## 十四、可审计性与运行目录

每次任务建议生成运行目录：

```text
runs/<task_id>/
    request.json
    file_profile.json
    normalize_plan.json
    normalized_tables/
    table_profiles.json
    relation_profile.json
    queries.sql
    join_validation.json
    result.csv
    report.md
    run.log
```

用户默认只看到结果，但系统应能回溯：

- 做了哪些清洗；
- 使用了哪些字段；
- 是否发生 Join；
- 是否有未匹配记录；
- SQL 是什么；
- 是否发生重试；
- 是否发生降级；
- 结果是否被截断。

## 十六、最佳实践

1. 标准表直接入仓，不浪费 Token。
2. 合并单元格和多级表头优先标准化，不直接拒绝。
3. 多表和多 Sheet 分析必须先做关系画像。
4. 高置信 Join 可自动执行，低置信 Join 需要轻确认。
5. LLM 不读取完整原始数据，只读取结构摘要、画像、样例和结果。
6. SQL 不展示给普通用户，但必须内部留存。
7. 指标口径有歧义时，确认业务含义，而不是确认 SQL。
8. 正式分析先生成脚本，再用脚本产生首次正式结果。
9. 脚本按 ETL 作业标准生成，至少具备参数化、可重跑、校验和运行产物。
10. Recipe 使用已验证脚本和结构化查询计划，不只做字符串替换。
11. Join 后必须验证行数膨胀和未匹配记录。
12. 降级对普通用户可透明，但审计日志必须记录。

## 十七、结论

调整后的方案保留原设计中“全自动、零 SQL 门槛、DuckDB 驱动、自然语言解读、模板沉淀”的优点，同时补强了复杂 Excel 标准化、多表关联、多 Sheet 关联、歧义确认、Join 验证、脚本优先复用和可审计性。

推荐 MVP 路线：

1. 第一阶段：标准表 + B 级轻度非标 + 单表 DuckDB 分析 + 脚本首次执行 + 解读输出；
2. 第二阶段：A1 复杂非标标准化 + 多 Sheet 入仓 + 脚本化运行目录；
3. 第三阶段：多文件多表 Join + 关系画像 + Join 验证 + 脚本复用；
4. 第四阶段：结构化 Recipe 元数据 + 脚本再生成 + 高级降级策略。
