## 一、激活触发条件评审

### 1.1 现有 triggers 列表

```
triggers:
  - karpathy
  - 卡帕西
  - 用karpathy视角
  - karpathy会怎么想
  - karpathy怎么看
```

### 1.2 发现的问题

#### 问题 A：`karpathy` / `卡帕西` 触发过于宽泛（严重）

这两个词是"姓氏级别"的触发词。用户说以下内容时会被误触发，但完全不需要 Karpathy 视角框架：

- "karpathy 最近的推文是什么？"（信息查询，非视角分析）
- "karpathy 的 GitHub 地址"（导航请求）
- "卡帕西是不是离开了 OpenAI？"（事实核实）
- "Hinton 和 Karpathy 谁更早做深度学习？"（比较性事实查询）

**风险等级：高**——会导致大量误激活，用户在高频使用中积累负面体验。

#### 问题 B：description 中的语义触发条件过于模糊（严重）

> "当用户请求用 Karpathy 视角分析问题、或问题涉及 AI/深度学习/LLM/编程范式/AI教育/AGI时，激活此框架。"

"问题涉及 AI/深度学习/LLM/编程范式/AI教育/AGI"覆盖了几乎所有技术对话。用户问"transformer 的 self-attention 怎么实现"时，需要的是一份技术解释，不是 Karpathy 视角。这意味着 Skill 会在 80%+ 的技术对话中被不必要地激活。

#### 问题 C：缺失高频自然表达（中等）

以下是用户可能使用的但没有被覆盖的表达：

| 用户实际可能说的 | 是否触发 | 原因 |
|-------------------|----------|------|
| "站在 karpathy 的角度看" | 可能不触发 | 无精确匹配 |
| "用 karpathy 的思维方式" | 可能不触发 | 无精确匹配 |
| "从 karpathy 的视角分析" | 可能不触发 | 无精确匹配 |
| "karpathy 会怎么做" | 可能不触发 | 只有"会怎么想/怎么看" |
| "用第一性原理分析" | 不触发 | 意图匹配但无触发词 |
| "从零构建的角度看" | 不触发 | 意图匹配但无触发词 |
| "vibe coding 的方式" | 不触发 | 意图匹配但无触发词 |

#### 问题 D：缺少排除条件（中等）

任何触发机制都需要负面清单。当前完全没有：

- 信息查询类请求不应激活 Skill
- 用户只是引用/提及 Karpathy 但不请求其视角
- 闲聊/寒暄不应激活
- 需要专业资质的领域（医疗/法律/金融）

### 1.3 触发条件评审总评

| 项目 | 评分 | 说明 |
|------|------|------|
| 意图匹配精度 | 2/5 | 覆盖了明确请求，遗漏了大量间接表达 |
| 误触发防控 | 1/5 | `karpathy` 作为 trigger 几乎必然误触发 |
| 自然语言覆盖度 | 2/5 | 缺少中文习惯表达 |
| 排除机制 | 0/5 | 完全没有 |

**结论：触发机制有根本性缺陷，需要从"关键词匹配"升级为"意图识别 + 排除条件"两层架构。**

## 二、角色扮演规则可操作性评审

### 2.1 问题路由

当前路由：Step 1 提供三类分叉（需要事实 / 纯框架 / 混合），但缺少**第四类：不适用/越界**。

| 路由类型 | 已有？ | 可操作性 |
|----------|--------|----------|
| 需要事实 → Step 2 研究 | 有 | 中（研究深度无约束） |
| 纯框架 → Step 3 直接回答 | 有 | 高 |
| 混合 → 先研究再框架 | 有 | 中（边界模糊） |
| 不适用 → 退出角色 | **缺失** | — |
| 敏感领域 → 拒绝 + 诚实说明 | **缺失** | — |

### 2.2 频率约束

现有约束：

> "不要在每条回复中都堆砌所有心智模型。选择与问题最相关的1-3个模型深入展开。"

**可操作性问题**：

1. "最相关"没有判定标准。当5个模型都与问题有某种关联时，如何选择？
2. "深入展开"没有定义。什么时候算"深入"？什么时候算"堆砌"？
3. 这个约束只针对心智模型，没有覆盖表达DNA（同样可能被过度使用，比如每句话都模仿括号内心独白会变得令人厌烦）。

### 2.3 失败预防

诚实边界（第7节）列出了7条"认识论边界"，但这是**声明**而非**行为指令**。AI 在执行时需要的是：

- "当遇到 X 类问题时，做 Y" 形式的规则
- 一个明确的**越界决策树**

当前缺失的越界规则：

| 场景 | 缺失的规则 |
|------|-----------|
| 用户问政治/宗教 | 诚实边界没说"跳出角色" |
| 用户问医疗/法律/金融建议 | 完全未提及 |
| 用户说"不确定/没想法" | 框架会不会强行套模型 |
| 搜索结果矛盾/不足 | 应对策略缺失 |
| 用户质疑角色扮演本身 | 如何处理元对话 |

### 2.4 核心原则优先级

现有5条核心原则：

1. 先判断问题类型，决定是否先做研究
2. 用心智模型分析，用表达DNA输出
3. 强断言 + 谦抑缓冲
4. 如果不能从零构建它，就不算真正理解它
5. 诚实标注不知道的

**问题**：
- 原则3（强断言）和原则5（诚实标注）可能冲突：一条要求"先给近似"，另一条要求"如实说不知道"。当对一个领域只有10%的了解时，给出一个90%正确的近似是否可行？还是应该直接说"我不了解"？
- 原则4（从零构建）和实际可操作性可能冲突：用户问一个复杂系统问题，AI 不可能真的现场构建，只能模拟构建过程。
- "核心价值观"（第8节）有优先级排序，但"核心原则"（第2节）没有。两个列表的关系不清晰。

另外值得注意的是，文档在"角色扮演规则"中列了5条核心原则，但后面"核心价值观"（第8节）又列了5条完全不同的内容并按优先级排列。这两个列表的职责划分不明确——到底哪个是运行时遵循的规则？

### 2.5 操作性总评

| 项目 | 评分 | 说明 |
|------|------|------|
| 问题路由完整性 | 3/5 | 缺少越界和退出路由 |
| 频率约束可执行性 | 2/5 | "最相关"无判定标准 |
| 失败预防 | 1/5 | 有声明无规则 |
| 原则冲突处理 | 1/5 | 无冲突处理机制 |

## 三、缺失的关键信息

### 3.1 未捕获的 Karpathy 重要思维特征

#### 3.1.1 "学习本身"的方法论

Karpathy 对"如何学习"有系统性思考（而不仅仅是从零构建）。他的 Zero to Hero 课程本身就是一种学习方法论：从最简单的单元开始、每一步都可运行验证、避免知识跳板。当前 Skill 只在"极简构建主义"中提到了构建，但缺少：

- **分层学习策略**：从 micrograd → makemore → GPT 的阶梯式认知构建
- **可运行验证原则**：每一步都必须产生可运行的输出，不能停留在理论理解
- **逐步增加复杂度的纪律**：不在一个概念还没被完全吸收时就引入下一个

#### 3.1.2 类比生成（Analogical Thinking）作为一种方法

Karpathy 不只是"使用"类比，他的核心能力之一是**生成新颖的、解释力极强的类比**：

- "LLM = OS kernel"
- "预训练 = 蹩脚的进化"
- "RL = 通过吸管吸取监督信号"
- "地球 = 很烂的计算机"

当前 Skill 在"计算系统隐喻"中列出了这些类比作为"内容"，但没有把类比生成作为**方法**给出。AI 在回答时需要知道：Karpathy 会主动创建新类比来解释概念，而不只是引用已有的类比。

#### 3.1.3 实验驱动的信念更新机制

"决策启发式"第10条提到了实验驱动更新，但这个问题值得深入作为一个完整的行为模式：

- Karpathy 多次在公开记录中展示"被实验证据说服 → 180度翻转立场"（Agent 从"无用"到"不可或缺"、RLVR 的重要性）
- 这不是简单的"知错能改"，而是一种**方法论上的激进经验主义**——理论框架必须屈服于实验证据
- 当前 Skill 缺少一个"当心，你现在的判断很可能是错的——如果有实验证据应该立即更新"的元规则

#### 3.1.4 对"生产率"和"工具体验"的敏感度

Karpathy 对工具体验极其敏感：
- PyTorch 赞美（"I've never felt better"）——好工具改变研究者状态
- 对 Cursor/Windsurf 的实时试用和点评
- "I don't think we appreciate just how amazing this is"——对工具进步保持惊叹

这种对工具体验的敏感度是他思维的重要组成部分，但在 Skill 中完全没有体现。

### 3.2 工作流死循环风险

#### Step 2 研究没有"足够好"的判定标准

当前描述：

> "如果回答质量会因为缺少最新信息而显著下降，就必须先研究。宁可多搜一次，也不要凭训练语料编造。"

**风险**：AI 可能陷入无限搜索循环——搜索 → 发现相关话题 → 搜索更多 → 发现更多相关 → ...，没有一个明确的停止条件。

**需要的约束**：
- 研究轮次上限（例如最多3轮搜索）
- "足够好"的判定标准（例如能回答核心问题就算完成）
- 时间敏感性的判断（今天的新闻事件 vs 长期趋势，研究深度应不同）

#### Step 1 的分类边界不清晰

"纯框架问题"和"混合问题"的边界在实践中非常模糊。几乎任何技术问题都带有某些事实背景——"你觉得大语言模型的未来是什么"是一个不需要最新事实的纯框架问题，但"2026年的大语言模型发展怎么样"就需要事实。两者之间的灰色地带很大。

### 3.3 诚实边界的遗漏

当前诚实边界7条全部是**认识论边界**（知识来源的限制），完全遗漏了**行为边界**：

| 遗漏的边界 | 严重程度 | 说明 |
|-----------|----------|------|
| 政治/宗教/社会争议话题 | 高 | Karpathy 刻意回避，反模式中提到了"反对政治话题"，但诚实边界中没有 |
| 专业资质领域（医疗/法律/金融） | 高 | 完全未提及。AI 不应以 Karpathy 身份给出这些领域的建议 |
| 个人攻击/道德评判 | 中 | Karpathy 不攻击个人，但规则中没有约束 |
| 角色分离失控 | 中 | 当用户开始把 AI 当成真正的 Karpathy 问私人问题时，需要降级机制 |
| 思维框架的适用边界 | 中 | 不是所有技术问题都适合用 Karpathy 框架——他明确不是某领域的专家（如强化学习的纯理论） |

### 3.4 其他缺失

| 缺失项 | 影响 |
|--------|------|
| Karpathy 对编程语言生态的看法（Python 的实用妥协 vs C 的极致控制） | 缺少完整的编程哲学维度 |
| Karpathy 的"Attention/专注"观——他对深度工作、碎片信息的看法 | 方法论维度缺失 |
| 角色退出机制——用户说"好的谢谢不用继续这个视角了"时的行为 | 交互体验问题 |
| 版本管理——Skill 如何随着 Karpathy 新观点自动或手动更新 | 维护性问题 |
| 回答长度控制——Karpathy 的推文极短、博客极长，AI 如何平衡 | 缺乏实用指导 |

```markdown
## 越界规则（角色退出条件）

以下情况应**退出 Karpathy 角色**，以普通 AI 身份诚实回答：

| 越界场景 | 退出方式 | 示例回复 |
|---------|---------|---------|
| 用户纯查询信息（"karpathy 什么时候写的这篇文章"） | 直接回答事实，不加框架分析 | "2025年10月，他在 bearblog 上发的。" |
| 用户问及政治/宗教/社会争议 | 引用反模式声明退出 | "Karpathy 刻意回避这类话题——我不应该用他的框架在这里。" |
| 用户需要专业资质（医疗/法律/金融建议） | 明确拒绝，给出方向建议 | "这不是 AI 或 Karpathy 能回答的问题，建议咨询专业人士。" |
| 用户开始把 AI 当成真实的 Karpathy | 降级为普通助手 | "我是一个 AI 助手，只是尝试用 Karpathy 的思维框架分析问题。" |
| 用户说"好了不用这个视角了" | 立即退出，恢复默认 | "好的，退出 Karpathy 视角。" |
| 问题需要领域专长但 Karpathy 没有 | 诚实标注，给出力所能及的部分 | "Karpathy 不是这个领域的专家，但基于他的通用框架，我认为..." |

**越界决策流程**：
收到问题 → 是否属于上述越界场景？→ 是：退出角色，诚实回答 → 否：正常进入 Step 1 分类。
```

**改动理由**：
1. 当前诚实边界只有"认识论边界"，完全缺少"行为边界"——越界规则填补了这个核心缺口
2. 每条越界场景都有具体退出方式，AI 可以直接遵循
3. 加入决策流程提高了可操作性：先判断是否越界，再走正常流程
4. 用户要求退出的场景被明确处理——这在实际使用中会高频出现

## 五、补充建议摘要

以下建议不要求逐一文本修改，但建议在后续迭代中考虑：

### 高优先级（影响可操作性）
