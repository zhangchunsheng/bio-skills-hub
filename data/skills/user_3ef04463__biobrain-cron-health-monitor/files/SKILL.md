# Cron Health Monitor — 定时任务健康卫士

## 一句话看懂

**它帮你盯着所有定时任务——哪个坏了、为什么坏、怎么修，全部自动处理。不让一个悄悄地坏掉。**

定时任务（cron）最可怕的地方不是报错，而是"成功但不干活"。它告诉你ok，其实什么都没做。等你发现已经是5天后了。

---

## 为什么要用这个？

你设了10个定时任务让AI自动干活：日报、巡检、发布、备份……但你怎么知道它们真的在干？

一个定时任务失败3天，可能没人发现。等到你发现的时候，这3天的数据已经找不回来了、内容已经断更了、客户已经跑了。

Cron Health Monitor就是解决这个的：自动巡检 + 自动诊断 + 自动修复。你只需要在它修不好的时候看一眼。

---

## 3分钟快速上手

### 第1步：看一眼所有定时任务状态（30秒）

告诉你的AI：

> "查一下所有cron job的健康状态"

它会列出每个任务：
- `consecutiveErrors`：连续失败几次（0=正常，1=注意，2+ =需要处理）
- `lastError`：最后一次错误信息
- `lastRunStatus`：ok 还是 error

### 第2步：发现有问题？套用故障速查表（1分钟）

| 错误信息关键词 | 原因 | 修法 |
|-------------|------|------|
| "Message failed" | 定时任务里的AI想发消息但发不出去 | 改用 `sessions_send` 发给主AI，别用 `message` |
| "LLM request failed" | AI模型太忙或不可用 | 换成免费模型 `zai/glm-4-flash`（知道能用） |
| "Write failed" | 写的文件路径不存在 | 先让AI创建文件夹，再写文件 |
| "Timeout" | 任务太复杂，做不完 | 加更多时间，或者把一个大任务拆成两个小任务 |
| 显示成功但实际没干活 | AI用太弱的模型糊弄了 | 换成付费模型，加一个验证步骤 |

### 第3步：一键修复（1分钟）

知道什么问题之后，告诉AI：

> "修一下这个cron job [任务名称]，错误是 [错误信息]"

它会自动判断是哪种故障，然后改配置、重新测试。5种常见故障全都在它的修复剧本里。

### 第4步：设定每周自动审计（30秒）

设一个周五22:00的定时任务：

> "设一个每周五晚上10点的巡检任务，检查所有cron的健康状态，有连续2天失败的立刻标记"

这样你就永远不用手动检查了。

## 故障速查手册

### 故障A："Message failed"（最常见）
定时任务里的AI想发消息但某些环境下发不出去。
**修法**：把任务指令里的"用message发到飞书"改成"用sessions_send发给main"。

### 故障B："LLM request failed"（第二常见）
用的AI模型名写错了，或者那个模型暂时不可用。
**修法**：把模型名改成 `zai/glm-4-flash`。这是一个稳定可用的免费模型。

### 故障C："Write failed"
AI想写文件但目标文件夹不存在。
**修法**：在任务指令里加一句"先创建文件夹，再写文件"。

### 故障D：超时
任务太复杂了，规定时间内做不完。
**修法**：加大时间限制，或者拆成两个小任务分别跑。

### 故障E："HEARTBEAT_OK"（假成功）
AI收到了任务但以为只是"打卡报到"，回了个ok就结束了。
**修法**：在指令里加一句"不要回复HEARTBEAT_OK，真正执行任务"。

### 🔴 故障F：假成功（最危险）
**这是最容易被忽视但最致命的一种**。定时任务显示"成功"，AI也写了很长一段看起来像干活的报告——但实际上什么都没干。

免费模型处理复杂任务（比如操控浏览器发布内容）时能力不够，会"假装干了"。没人发现的话，你可能以为内容一直在发，其实停了5天。

**怎么发现**：不要看定时任务报告，去看目标平台有没有真正出现内容。

**怎么修**：
1. 对外发布类任务换成付费模型（不要用免费模型）
2. 在任务指令里加一句："做完后去平台验证一下内容是否真的发布了"
3. 重要任务加入外部验证——看平台后台，不是看AI报告

## 常见问题 FAQ

**Q：什么是"consecutiveErrors"？怎么不用"consecutive"这种词？**
A：你可以理解成"连续失败次数"。比如今天失败了，明天又失败了——那就是2次连续失败。0次是正常，1次要警惕，2次以上需要处理。

**Q：为什么不要一次失败就报警？**
A：有时候模型刚好卡了一下、网络抖了一下，下一次就恢复了。一次失败就报警容易变成"狼来了"，你真的需要看的时候已经麻木了。2次连续失败才报警，把偶然故障过滤掉。

**Q：我的定时任务显示"ok"但是内容没发布，是真的吗？**
A：完全可能。这就是"假成功"。AI可能用了太弱的模型，看起来像干活了其实没干。你最好亲自去平台看看内容有没有真的出现。

**Q：免费模型和付费模型怎么选？**
A：很简单：内部任务（写笔记、巡检、学习）用免费的；发到外面的任务（发布内容、回复用户）用付费的。免费模型处理不了浏览器操作等复杂任务。

**Q：自动修复靠谱吗？**
A：5种常见故障的修复方法是经过几十次生产验证的，成功率很高。但如果一种故障它没见过（不在5种里），它会标记出来让你看。它不会装懂。

**Q：我需要了解"cron"的代码吗？**
A：不需要。整个过程你用自然语言告诉AI就行，它会帮你操作。

## 运行时稳定性保障（QP 韧性体系）

本技能为 Prompt 型技能，稳定性通过以下机制保障：

### 输出一致性校验
- 同一输入多次运行时，核心结论应一致（允许表达方式差异）
- 若输出出现显著矛盾，优先回溯最后一次修改的源头
- 引用型数据以原始来源为准，不因模型采样差异改变结论

### 异常输入降级链
```
正常输入 → 完整流程
    ↓ 关键信息缺失
    追问补充（1轮）→ 仍不足？→ 标注「信息不足」+ 给出最小可行输出
    ↓ 超出能力边界
    硬边界拦截 → 明确告知「不在能力范围」+ 建议替代方案
    ↓ 模型采样不稳定
    核心结论不变 → 仅标注「表达可能存在微调」
```

### 重试与恢复指引
| 场景 | 处理 |
|------|------|
| 输出明显偏离工作流程 | 用户可追加「请严格按工作流程重新执行」触发重试 |
| 数据引用不一致 | 以首次引用来源为准，后续引用追加「已核实与首次一致」 |
| 中间步骤遗漏 | 用户可指定步骤号要求补执行 |
| 外部依赖不可用 | 标注「外部依赖暂不可用」+ 使用缓存/已知数据替代，不静默跳过 |

### 用户干预入口
- 任何步骤输出不满足预期时，直接指出问题即可触发修正
- 不需要重新描述全部需求，模型保留上下文并增量修正
- 连续 2 轮修正失败 → 建议缩小范围或拆分子任务
