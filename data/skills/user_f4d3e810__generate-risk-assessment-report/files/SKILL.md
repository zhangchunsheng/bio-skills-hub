# 通用风险评估报告

## 目标

把分散材料转化为可核验、可排序、可行动的风险判断。报告必须回答：评什么、依据什么、风险如何形成、现有控制是否真实有效、控制后还剩什么风险、谁在何时采取什么行动、如何监测和升级。

本 Skill 是跨领域通用框架。若核心任务是供应商入库或资格准入，优先使用专门的供应商准入 Skill；若核心任务是投资尽调、行业投资策略或用户真实账户投资建议，使用对应专门 Skill。

## 工作模式

先判断请求属于以下哪一种，并在报告首页说明：

1. **生成**：依据原始材料形成完整报告。
2. **改写**：保留已有事实和口径，重构逻辑、证据与行动项。
3. **审查**：检查事实、方法、分级、控制有效性、结论和闭环缺陷。
4. **快速评估**：材料有限时形成 1—3 页管理层版；所有缺口标为“待核实”，不得伪装成完整尽调。

## 第一步：锁定评估口径

明确并记录：

- 评估对象、业务目标、决策问题和报告使用者；
- 组织、地域、系统、流程、项目阶段与排除范围；
- 评估基准日、数据截止日和风险时间跨度；
- 适用法律、监管要求、合同、内部制度和行业标准；
- 风险偏好、容忍度、红线与分级标准的来源；
- 重大性口径、影响维度、评估方法和批准主体。

缺少会改变结论的口径时，只问最少的针对性问题。若用户要求先出草案，采用显式假设并在首页列示，不能把默认矩阵写成组织正式标准。

## 第二步：建立证据台账

为每个关键判断记录：

| 字段 | 要求 |
|---|---|
| 证据编号 | 唯一、可追溯 |
| 事实或控制主张 | 一条主张对应一项或一组证据 |
| 来源与定位 | 文件名、页码/条款/表格/访谈对象或公开链接 |
| 截止时间与适用范围 | 防止过期或跨主体误用 |
| 证据状态 | 已核验、部分核验、自述、冲突、缺失 |
| 置信度 | 高、中、低，并说明原因 |

优先级通常为：可复核原始记录和外部权威材料 > 经批准的内部记录 > 访谈或自述。来源冲突时并列呈现，不擅自选择有利版本。报告必须区分事实、分析判断、假设和待核实事项。

## 第三步：识别风险

先从目标、关键流程、关键资产、利益相关者和外部环境出发，再使用分类清单补漏。每项风险写成：

> 因为【原因/脆弱性】，在【条件或时间窗口】可能发生【事件】，从而对【目标/资产/利益相关者】造成【影响】。

不要把原因、事件、后果或已有问题混写成风险标题。风险已实际发生时，单列“已发生事项”，并评估其后续风险。

至少检查战略、市场、运营、财务、法律合规、廉洁、人员、项目、供应链与第三方、质量、生产安全、环境、信息与数据、声誉和外部事件；按对象裁剪，不为凑齐类别制造风险。

## 第四步：评价固有风险

固有风险是假设不考虑现有控制时的风险。对每项风险分别评价：

- 发生可能性；
- 财务、运营、合规、安全、环境、数据、声誉等影响；
- 风险速度、持续时间、可探测性和不可逆性；
- 与其他风险的相关性、共同原因、集中度和传导路径；
- 置信度与证据缺口。

使用机构或项目既有标准。没有标准时，可使用 [methodology.md](references/methodology.md) 的 5×5 示例，但必须标注“分析假设”。风险矩阵是序数型排序工具，不能据此计算损失期望值，也不能把不同风险分数相加或平均成“总体风险值”。

## 第五步：评价控制与剩余风险

按预防、发现、纠正/恢复分类控制，并分别评价：

1. **设计有效性**：控制是否针对风险原因或影响，责任、频率、阈值和升级路径是否明确。
2. **运行有效性**：是否有样本、日志、审批、演练、测试、审计或运行记录证明控制实际执行。

制度存在、证照存在或管理层自述不等于运行有效。若运行证据不足，剩余风险应标为“无法可靠确定”或使用明确的保守假设，不得自动降级。

剩余风险必须基于已验证控制后的可能性和影响重新评价。红线、法律禁止、重大安全或伦理底线可覆盖矩阵分值，直接触发不可接受或升级。

## 第六步：形成结论与处置

逐项对照风险偏好、容忍度、红线和决策门槛，给出以下之一：

- 可接受并监测；
- 有条件接受并整改；
- 不可接受，暂停/规避/升级；
- 证据不足，暂缓判断。

项目或方案总体结论使用“推进、有条件推进、暂停、终止、证据不足”之一，并列明尚未满足的阶段门；不得用总体结论覆盖单项红线。

风险处置可采用规避、降低、转移/分担或接受。每项行动必须包含责任人、绝对日期、资源或前置条件、验证方式、**目标剩余风险（管理目标）**、关键风险指标、触发阈值、升级路径和应急/退出方案。目标剩余风险不等于控制实施后已经验证的剩余风险。没有组织阈值时写“待授权批准”，可先使用法定、合同或测试通过/失败等客观阶段门。不得把“加强管理、持续关注”当作完整措施。

对重大或高速度风险开展至少一个合理不利情景；有可靠概率和金额数据时才能计算期望损失、敏感性或压力测试。没有可靠数据时使用定性情景并标明假设。

## 第七步：生成报告

按 [report-template.md](references/report-template.md) 输出。管理层摘要前置：

- 一句话总体判断；
- 3—10 项优先风险；
- 红线或不可接受事项；
- 关键证据缺口；
- 需要批准的行动与时间节点。

风险清单至少包括风险编号、因果链、领域、证据、固有风险、关键控制、控制证据、剩余风险、偏好对照、处置、责任人、期限、KRI、触发条件与置信度。信息不足时保留空值和“待核实”，不补造数字。

## 自动评分与质检

若用户提供结构化 JSON 风险清单，可运行：

```bash
python3 scripts/score_risks.py input.json --format markdown
```

脚本只按用户提供或明确选择的矩阵计算排序；缺少剩余风险时不会推算。输出须结合红线和证据状态人工复核。

完成报告后运行：

```bash
python3 scripts/validate_risk_report.py report.md
```

修正所有错误；对警告逐项判断并在报告中解释。严格审查时加 `--strict`。

## 审查现有报告

审查结果按严重程度分级：

- **致命**：结论无证据、重大红线被分数覆盖、剩余风险无控制证据、无可靠数据/模型/授权假设仍输出精确概率或损失、评价对象或口径错误。
- **重大**：固有/剩余风险混淆、控制设计与运行不分、未对照偏好、重大风险无责任人/期限/触发器、范围或截止日缺失。
- **一般**：定位不完整、措辞含混、图表与正文不一致、行动验证方式不足。

逐条写明：问题位置、问题事实、影响、修正建议和所需证据。不要仅给一个审查总分。

## 强制质量规则

- 不承诺“零风险、绝对安全、完全消除、保证不发生”。
- 不把高风险自动解释为不应决策；应结合收益、偏好、处置与替代方案。
- 不把低概率高影响风险因乘积分数低而忽略。
- 不把第三方评级、认证或保险视为风险转移完成。
- 不把风险接受写成分析人员决定；必须标明有权批准者和依据。
- 不用总分掩盖单项重大风险、否决项、红线或证据缺口。
- 不将报告结论写成法律、审计、鉴证、安全认证、中标或投资承诺。
