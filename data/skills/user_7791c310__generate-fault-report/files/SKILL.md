# 故障报告生成器

将markdown格式的故障处理记录转换为专业的HTML故障分析报告。

## 输出定位

- 输出对象：甲方客户、项目管理方、运维负责人
- 输出身份：云计算厂商乙方技术支持 / 研发 / 交付团队
- 输出目标：以事实为基础，形成专业、审慎、委婉、可执行的正式故障分析报告

## 写作原则

### 1. 保持厂商正式口径

- 用词正式、克制，避免口语化表达
- 优先使用“经排查确认”“初步判断”“结合当前证据分析”“建议在维护窗口内执行”等表述
- 避免使用“应该”“大概率就是”“肯定是”“重启试试”这类不专业或过强判断

### 2. 事实、分析、方案分层

- **事实层**：只写实际观测到的现象、日志、配置、告警、截图、时间线
- **分析层**：说明为何形成当前判断，明确“已确认”“初步判断”“待进一步核验”
- **方案层**：统一放在报告最后的“临时处置方案”和“长期治理方案”中
- **图文层**：图片必须跟随对应排查点展示，不要将多张图片集中堆放在一个节点段落末尾

### 3. 保持委婉与可审阅性

- 不直接归责，不使用带情绪或指责色彩的表达
- 如证据不足，不下绝对结论，应写为“当前证据指向……，仍需结合后续验证进一步确认”
- 如涉及客户侧配合，表述为“建议与客户侧共同确认……”“建议在双方约定维护窗口内执行……”

### 4. 固定章节、固定字段

- 严格保持固定章节输出
- 不因输入材料多少而随意删改主章节
- 如材料不足，可保留章节并以审慎措辞说明“当前未获取到相关证据”

## 固定输出结构

生成结果必须保持以下固定章节与固定字段，不随输入材料自由变形：

### 一、故障情况描述

- 故障现象
- 影响范围
- 发现时间 / 恢复时间
- 详细排查经过（按节点或组件展开）

### 二、原因分析

- 已确认原因
- 初步判断
- 排除因素

### 三、处置与治理方案

- 临时处置方案
- 长期治理方案

如某字段缺失，保留字段名称，并以“当前暂未获取到直接证据”或“待进一步核验”说明，不得直接删除字段。

## 工作流程

### 1. 读取markdown源文件

读取用户提供的markdown故障日志，识别以下关键部分：

**必需提取的信息：**
- 客户名称、问题描述（故障主题）
- 故障发生时间
- 云平台版本、产品版本
- 故障现象描述
- 各节点/组件的详细排查信息（节点名、SN号、受影响OSD、问题描述、排查结论）
- 已确认原因、初步判断、排除因素
- 临时处置方案与长期治理方案

**图片URL识别：**
- 查找所有图片链接（通常是COS、OSS等云存储URL）
- 区分故障现象截图和节点配置截图
- 保留原始URL，不要修改

### 2. 解析markdown结构

典型的markdown故障日志结构：

```markdown
## 环境信息
- 客户：XXX
- 时间：202X年X月X日
- 版本：ZStack Cloud X.X.X

## 故障现象
[描述 + 图片URL]

## 详细排查经过

### 节点 xxx-xx (SN: xxx)
- 受影响OSD: osd.xx
- 问题：[描述]
- 排查结论：[结论]
- [可选：图片URL]

### 节点 xxx-xx (SN: xxx)
...

## 故障结论
### 已确认原因
1. [原因1]
2. [原因2]

### 初步判断
- [基于当前证据形成的判断1]

### 排除因素
- ✓ [因素1]

## 处置与治理方案
### 临时处置方案
- [措施1]

### 长期治理方案
- [措施1]
```

- 未指定品牌：默认使用 ZStack 版
- 用户提到 `阿里云`、`阿里云卖出去的产品`、`阿里云 Logo`、`阿里云团队`：使用阿里云版
- 仅允许替换品牌元素（Logo、主色、默认团队名称），其余内容结构保持一致

**关键替换规则：**

### 3.1 正式文案要求

生成报告时，优先遵循以下文风约束：

- 故障现象：描述业务影响、影响范围、发现方式，不夸张，不口语化
- 节点详情：按排查点分段描述观察结果、日志现象、配置差异、影响对象；每个排查点后紧跟对应图片，不在节点末尾集中堆图，也不在每个节点后面给出随意处置建议
- 根因分析：固定分“已确认原因”“初步判断”“排除因素”三类组织
- 临时处置方案：强调止血、恢复、隔离、验证，语气要稳妥
- 长期治理方案：强调治理、优化、预防、机制建设，避免空泛口号

推荐用语示例：

- “经现场排查确认……”
- “结合当前日志与配置表现，初步判断……”
- “当前未发现……相关证据，可暂不作为本次直接诱因。”
- “建议在双方约定的维护窗口内执行……”
- “为降低同类风险重复发生的概率，建议后续……”

避免用语示例：

- “大概率就是……”
- “重启试试……”
- “明显是……的问题”
- “肯定是客户环境导致……”

### 4. 图片处理规则

- 如果同一排查点有 2 张图片，可在该排查点下使用并排布局；如果属于不同排查点，则拆开分别展示

## 关键注意事项

### 必须保留的HTML特性
1. **可编辑功能**：所有`.editable`类元素保持`class="editable"`
2. **JavaScript脚本**：完整的编辑模式切换和保存逻辑
3. **CSS样式**：包括打印优化的`@media print`规则
4. **Logo图片**：
   - ZStack 版：使用默认 ZStack Logo 或用户指定的URL
   - 阿里云版：使用默认阿里云中文 Logo 或用户指定的URL

### Markdown到HTML映射要点
1. **节点编号**：按markdown中出现顺序编号（1. 2. 3. ...）
2. **列表转换**：markdown的`- item`转为`<li>item</li>`
3. **加粗文本**：markdown的`**text**`转为`<strong>text</strong>`
4. **图片alt文本**：根据上下文生成有意义的alt描述

### 常见markdown变体处理

**变体1：节点信息分散在不同标题下**
```markdown
## zstack-86节点
### 问题
...
### 处理
...
```
→ 合并到一个`node-detail`块中

**变体2：没有明确的SN号**
```markdown
## 节点 zstack-86
```
→ h4标题只写节点名：`1. 节点 zstack-86`

**变体3：图片URL嵌入在文字中**
```markdown
如下图所示：![图](URL)
```
→ 提取URL，放入标准的`image-container`结构

生成HTML后验证：
- [ ] 所有markdown中的图片URL都已嵌入HTML

- [ ] 基本信息表已填充（客户名、时间、版本等）
- [ ] 故障现象描述完整
- [ ] 每个节点都有排查结论（recommendation-box）
- [ ] 原因分析和处置/治理方案已填充
- [ ] JavaScript编辑功能完整保留
- [ ] CSS打印优化规则完整
- [ ] 文件保存在Downloads目录
- [ ] 最终方案区仅包含“临时处置方案”和“长期治理方案”

## 故障等级定义（P1-P4）

根据钉钉文档标准，故障级别分为P1-P4四个等级：

### P1：一级故障（紧急）
**定性：** 生产环境出现数据丢失，或云平台完全不可使用，已直接造成严重商业损失，或对客户公司声誉产生极其恶劣的影响。任何应急措施均已失效。

**关键特征：**
- **数据层面：** 生产环境数据发生丢失、损坏且无法通过常规备份恢复，影响业务核心数据安全。
- **平台层面：** 云平台所有核心功能（如计算、存储、网络）全面瘫痪，客户无法登录平台或使用任何服务。
- **影响层面：** 已导致客户核心业务（如交易系统、支付系统）全面停摆，产生直接经济损失；或引发媒体负面报道、监管问询等声誉危机。

**说明：**
- KA客户同个P2级别故障类问题2次以上发生，可以定义为P1故障
- 本身是P2或者P3问题，在处理过程中出现了P1故障，需要升级到P1故障

### P2：二级故障（高）
**定性：** 云平台关键组成部分不可用，或存在影响关键业务的高风险，已影响客户环境使用。

**关键特征：**
- **平台层面：** 云平台关键模块（如出现大部分主存储系统、物理机集群、网络链路等）不可用，影响业务核心环节。
- **应急状态：** 客户已启动自身应急方案（如切换至备用存储、启用备用网络），核心业务暂时不受影响，次要业务受影响。
- **影响层面：** 客户关键业务已受影响，且任何应急措施均已失效，已引起较大的商业损失。

### P3：三级故障（中）
**定性：** 云平台仅个别组件或节点出现故障，核心产品仍可运转但功能存在限制，未对客户整体业务运作造成严重制约，情况无需紧急处理。

**关键特征：**
- **平台层面：** 云平台非核心组件故障，核心功能（计算、主存储、核心网络）正常。
- **业务影响：** 客户次要业务（如数据备份同步、时间不同步）出现问题，核心业务（如交易、用户核心操作）不受影响。
- **运行状态：** 产品整体可正常使用，仅部分功能非关键配置项受限，客户可通过调整业务流程暂时规避影响。

### P4：四级故障（低/咨询）
**定性：** 非故障或者没有任何不良运行情况，平台操作使用相关问题。

**关键特征：**
- **平台层面：** 平台无异常，功能使用咨询。
- **业务影响：** 业务正常运行，新部署业务中遇到问题咨询。
- **适用范围：** 任何不涉及远程的咨询类型问题。

### 故障级别选择与显示规则

在生成报告时，根据markdown中的描述智能判断故障级别，并**只显示确定的那一个等级**：

**判断逻辑：**
1. **分析markdown内容**，查找关键词：
   - "数据丢失"、"完全不可用"、"全面瘫痪"、"核心业务停摆" → P1
   - "关键模块不可用"、"启动应急方案"、"较大商业损失"、"关键业务受影响" → P2
   - "个别组件故障"、"核心功能正常"、"次要业务受影响"、"非核心组件" → P3
   - "咨询问题"、"功能使用疑问"、"平台无异常"、"操作咨询" → P4

2. **生成HTML时**，故障级别字段只显示确定的等级格式：
   ```html
   <td class="value editable">P2（二级-高）</td>
   ```
   **不要**显示为：
   - ❌ `☐ P1（一级-紧急） ☐ P2（二级-高） ☐ P3（三级-中） ☐ P4（四级-低/咨询）`
   - ❌ `[P1/P2/P3/P4]`

3. **如果无法判断**，默认使用P3，并在SKILL.md中说明原因让用户自行修改

**示例：**
- markdown提到"核心功能正常，仅部分非关键配置项受限" → 生成 `<td class="value editable">P3（三级-中）</td>`
- markdown提到"生产环境数据丢失，无法恢复" → 生成 `<td class="value editable">P1（一级-紧急）</td>`
