# General-skill-reviewer 评审示例

> 以下展示对一个中等质量 Skill 的部分审计输出，作为评审严格程度的标杆。
>
> **⚠️ 仅为格式和严格程度参考，不可照搬具体内容。每次评审必须基于被审 Skill 的实际内容。**

---

## 示例：对"数据清洗 Skill v1.0"的维度 A + C 审计

### Step 1 量化统计块

```
总行数：487 行
估算 token 数：~7,300 tokens
硬规则总数：38 条（含"必须"19条、"禁止"12条、"不得"7条）
P0 规则数：3 条（位于第 12-14 行）
```

### 维度A：架构与Token经济性 — 7/15

审计项1：主体行数
  状态：⚠️需改进
  证据：487 行，超过 400 行阈值 87 行。其中 §3"常见脏数据模式速查表"占 62 行（第 201-262 行），全部为 LLM 已知的通用清洗模式（空值/重复行/类型错误）。
  建议：将 §3 速查表移至 reference.md，主体预计降至 ~425 行；进一步精简 §2.4 的通用 Python 库介绍（pandas/numpy 是 LLM 已知知识），预计降至 ~390 行。

审计项2：渐进式披露
  状态：❌不通过
  证据：所有内容集中在单一 SKILL.md 中，无 reference.md 或 examples.md。§3 速查表（62行）和 §5 输出示例（45行）可独立文件分离。
  建议：拆分为 SKILL.md（~380行）+ reference.md（速查表）+ examples.md（输出示例）。

### 维度C：规则工程质量 — 9/20

审计项C1：硬规则计数
  状态：❌不通过
  证据：38 条硬规则，超过 25 条阈值。按功能分类：输入验证 12 条、转换规则 14 条、输出校验 8 条、异常处理 4 条。
  建议：输入验证的 12 条中有 5 条可合并为 2 条条件-动作规则（如"当列类型为 string 且期望为 numeric → 尝试 pd.to_numeric，失败则标记为异常"可覆盖当前的 #7/#8/#9 三条独立规则）。

审计项C3：规则格式检查
  状态：⚠️需改进
  证据：38 条中有 11 条为描述性原则，如第 87 行"要注意数据类型一致性"、第 134 行"应确保输出结果的完整性"。
  建议：
  - 当前写法（第 87 行）："要注意数据类型一致性"
  - 改为："当源列类型与目标 schema 不匹配时 → 按 schema 定义的类型转换规则执行强制转换，转换失败的行写入 error_log"

审计项C4：正向/负向比例
  状态：❌不通过
  证据：正向 19 条（50%）、负向 19 条（50%），低于 70% 正向阈值。可改写示例：
  - 当前（负向）："禁止静默丢弃异常行"
  - 改为（正向）："所有处理异常的行写入 error_log 并在最终报告中汇总"

---

> **以上审计输出体现的标杆**：
> 1. 每个"不通过"都引用了具体行号和原文
> 2. 建议给出了"当前→改为"的完整对照
> 3. 统计用精确数字（38条、11条、50%）而非模糊描述
> 4. 合并建议附带了具体的合并方案（哪几条可以合并为什么）
