## 一、知识条目

技术与项目离线索引位于 `技术项目索引.json`。每个条目至少包含：

| 字段 | 说明 |
| --- | --- |
| id | 稳定英文标识 |
| kind | technology、method 或 project |
| name / aliases | 规范名称和中英文别名 |
| technology / methods | 技术大类和可选方法 |
| summary / principle | 是什么和原理 |
| common_measurements | 常见指标名称，不等于通用阈值 |
| qc_stages | 可选质控阶段 |
| reference_file | 对应详细参考文件 |
| sources | 权威原始来源和核对日期 |
| scope_note | 适用范围及不能推广的内容 |

推荐质控阶段：

1. 申请与样本接收
2. 样本质控
3. 核酸提取
4. 反应体系或文库制备
5. 扩增、杂交或上机
6. 下机数据或信号质控
7. 结果判读
8. 报告审核

不要为了套模板创建用户业务中不存在的阶段。

## 二、v1.1 顶层结构

正式生成器输入由以下字段组成：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `$schema` | 否 | 建议指向 `references/qc-flow.schema.json` |
| schema_version | 是 | 正式模板固定为 `1.1` |
| diagram | 是 | 图页、业务分类、来源和布局 |
| measurements | 是 | 结构化指标定义，可为空数组 |
| nodes | 是 | 业务节点 |
| edges | 是 | 有向连线 |

完整机器约束以 `qc-flow.schema.json` 为准。

## 三、diagram

| 字段 | 说明 |
| --- | --- |
| name / id | 图页名称和唯一英文 ID |
| technology | PCR、NGS、Sanger、FISH 等 |
| method | qPCR、扩增子建库、分离探针等；未知时写“未确定” |
| project | BRAF V600E、ALK 重排或通用模板 |
| qc_stage | 本图覆盖的总体质控阶段 |
| stages | 泳道或节点阶段的有序列表 |
| sources | 可追溯来源数组 |
| layout | 普通流程、泳道和页面设置 |

### 3.1 来源字段

每个来源包含：

- id
- type：user-file、laboratory-sop、validation-report、manufacturer-ifu、regulatory、professional-guideline、public-database、official-technical-document 或 user-confirmed
- title
- version
- last_verified
- url 或 path
- scope_note
- evidence_status：confirmed、inferred、unknown 或 conflict

用户资料的“已确认”表示图中确实存在该规则，不表示该规则可推广为行业标准。

### 3.2 布局字段

| 字段 | 说明 |
| --- | --- |
| mode | `flow` 或 `swimlane` |
| page_width / page_height | 最小或固定页面尺寸 |
| auto_size | 是否按节点和来源说明自动扩展页面 |
| show_source_note | 是否在图中显示证据与适用范围 |
| center_x / start_y | 主通道和起始位置 |
| level_gap / lane_gap | 层级和分支间距 |
| stage_gap / margin | 泳道间距和页面边距 |

## 四、measurements

每个指标包含 id、name、unit、description 和 evidence_refs。指标定义用于绑定条件，不代表已存在数值阈值。

示例：

    {
      "id": "fam_ct",
      "name": "FAM Ct",
      "unit": "Ct",
      "description": "用户样例中的靶标通道读数",
      "evidence_refs": ["user_braf_drawio"]
    }

## 五、节点

### 5.1 节点类型

| type | 用途 | 默认样式 |
| --- | --- | --- |
| start | 输入或开始 | 灰色圆角 |
| process | 计算、处理或人工复核 | 蓝色圆角 |
| decision | 条件判断 | 黄色菱形 |
| positive | 阳性终点 | 绿色圆角 |
| pass | 通过终点 | 绿色圆角 |
| negative | 阴性终点 | 灰色圆角 |
| invalid | 无效或失败终点 | 红色圆角 |
| warning | 灰区、复检或待处理过程 | 橙色圆角 |
| end | 普通结束或人工处理终点 | 灰色圆角 |

### 5.2 公共字段

每个节点必须提供 id、type、label、stage 和 evidence_refs。可用 x、y、width、height、level、lane 和 style 覆盖默认布局或样式。

decision 必须增加 condition；positive、pass、negative、invalid、end 必须增加 terminal_result。

## 六、结构化条件

condition 包含 operator、expression 和 missing_policy。非 CUSTOM 条件还要引用 measurement。

| operator | 含义 | 主要字段 |
| --- | --- | --- |
| EQ / NE | 等于 / 不等于 | value |
| LT / LE | 小于 / 小于等于 | value |
| GT / GE | 大于 / 大于等于 | value |
| BETWEEN_CLOSED | 闭区间 | lower、upper |
| BETWEEN_OPEN | 开区间 | lower、upper |
| IN | 枚举集合 | value 数组 |
| EXISTS / MISSING | 存在 / 缺失 | measurement |
| CUSTOM | 无法在当前资料中数值化的 SOP/IFU 规则 | expression |

missing_policy 可选 fail、pass、invalid、next_branch、manual_review 或 not_applicable。

缺少项目阈值时应使用 CUSTOM，例如：

    {
      "operator": "CUSTOM",
      "expression": "依据当前 panel、pipeline 和实验室验证规则判断",
      "missing_policy": "manual_review"
    }

## 七、终点

terminal_result 用于把显示文字和机器语义分开，可选：positive、negative、pass、invalid、manual_review 或 end。

每个流程至少有一个明确终点；每个业务节点都必须能够到达某个终点。允许“复检/重做”回环，但回环必须有终点出口。

## 八、连线

每条连线包含：

- id、source、target
- label：判断出口必须非空且同一判断节点下唯一
- branch：next、yes、no、pass、fail、positive、negative、invalid、manual_review 或 repeat
- evidence_refs
- 可选 style

同一判断节点的 branch 语义也必须唯一。

## 九、ID 和证据规则

1. ID 使用英文字母开头，可包含数字、下划线、点或连字符。
2. `_meta_` 和 `_stage_` 是生成器保留前缀，业务对象不能使用。
3. 节点与连线 ID 不得冲突。
4. evidence_refs 必须指向 diagram.sources 中真实存在的来源 ID。
5. 指标条件中的 measurement 必须指向 measurements 中真实存在的 ID。

## 十、v1.0 兼容

生成器保留旧版 `diagram.source`、无 stage/evidence_refs/branch/terminal_result 的输入兼容：运行时复制并补充兼容字段，不回写旧文件。正式新增或修改模板必须使用 v1.1，不能继续扩展旧格式。

## 十一、阈值边界

每个数值条件都要保留指标、运算符、数值或范围、单位、空值策略、来源和适用范围。不要只保存自然语言，也不要把厂家或单个实验室阈值变成通用技术结论。
