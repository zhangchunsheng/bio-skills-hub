# 出 MD 方案 (Generate Tech Plan)

本 skill 是标准开发流程的第 4 步：前三条都确认完毕后，输出一份明细级的技术方案文档（Markdown 格式），详细到"照着这个文档开发不会出问题"的程度。

## 前置条件
- 第 1 步"需求确认卡"已用户确认
- 第 2 步"代码现状摘要"已用户确认
- 第 3 步"盲区"已用户确认解决

## 执行规则

### 1. 方案内容结构
方案文档必须包含以下部分：

| 部分 | 来源 / 说明 |
|------|-------------|
| 需求概述 | 来自第 1 条需求确认卡 |
| 现有代码现状 | 来自第 2 条代码现状摘要 |
| 业务规则 / 关键约定 | 来自第 3 条搞懂的结论 |
| 技术设计 | 整体思路、模块划分、核心逻辑、数据结构 / 接口设计、关键流程 |
| 改动清单 | 要新建哪些文件、修改哪些文件、各做什么 |
| 边界与风险 | 需要注意的坑、兼容性考虑 |
| 验收标准 | 细化后的验收标准 |
| Task 拆分雏形 | 为第 6 条铺垫，初步的 Task 划分 |

### 2. 明细级要求
- 方案要具体到**函数级别的设计思路 + 关键代码片段**（伪代码或核心逻辑）
- 尽量做到**接近能直接 copy 的代码骨架**级别，让后续写代码时无需再动脑子
- 不能只写"实现 XX 功能"这种空话

### 3. 自己内部 review 一遍
- 输出方案后，先自己内部 review 一遍，检查：
  - 方案完整性：是否覆盖了需求的全部要点
  - 逻辑自洽：各部分之间是否有矛盾
  - 有无遗漏：边界情况、异常处理、兼容性是否考虑到
- 内部 review 通过后，再提交给用户审阅（进入第 5 步）

## 输出格式示例

```markdown
# 技术方案：xxx

## 一、需求概述
（来自需求确认卡）

## 二、现有代码现状
（来自代码现状摘要）

## 三、业务规则 / 关键约定
（来自盲区解决结论）

## 四、技术设计
### 4.1 整体思路
### 4.2 模块划分
### 4.3 核心逻辑（含关键代码骨架）
### 4.4 数据结构 / 接口设计
### 4.5 关键流程

## 五、改动清单
| 操作 | 文件 | 说明 |
|------|------|------|
| 新增 | xxx | xxx |
| 修改 | xxx | xxx |

## 六、边界与风险

## 七、验收标准

## 八、Task 拆分雏形
```

## 注意事项
- 方案越详细，后续开发和拆 Task 越省力，不要偷懒
- 代码骨架要结合现有代码风格，不要凭空造不存在的 API
- Task 拆分雏形只是铺垫，第 6 步会正式细化和确认
- 内部 review 是自我把关，避免把有明显漏洞的方案直接丢给用户
