## 一、核心哲学

### 1.1 双铁律

> **铁律一：调研不是资料的堆砌，是洞察的提炼。**
> **铁律二：报告不是信息的容器，是决策的杠杆。**

一份罗列了某领域所有产品功能的文档是百科条目；一份包含"底层逻辑是什么""隐藏假设是什么""真正有价值的交叉点在哪里"的文档才是调研报告。前者把信息搬运到一起，后者把信息转化为可行动的洞察。

### 1.2 四个底层认知

| 认知 | 说明 |
|------|------|
| **历史纵深先于技术前瞻** | 任何AI应用都不是凭空出现的，都有历史前例可循。传统模式中蕴含着经过时间验证的设计智慧。不调研历史，就会重复造轮子。 |
| **并行先于串行** | 把一个大主题拆解为三个独立子维度并行调研，比线性调研效率高3倍，且能发现单一维度看不到的交叉洞察。 |
| **AI是增强不是替代** | 最有价值的创新往往在"传统智慧与AI能力的交叉点"——用AI增强传统模式中被验证有效的设计，而非推翻重来。 |
| **落地蓝图是终点** | 调研的最终目的不是"了解"，而是"能做"。每份报告必须以可执行的架构蓝图和行动建议收尾。 |

### 1.3 方法论起源

本技能的方法论提炼自一次完整的"AI+领域"深度调研实践。该实践对目标领域进行了三维度并行调研（历史脉络与设计特征、AI驱动架构、交互设计模式），整合后生成了包含10个章节、12张表格、3张架构图、48条引用来源的结构化HTML报告。实践验证了"五层递进 + 三维度并行"框架的有效性，本技能将其抽象为可复用的通用方法论。

## 二、方法论核心：五层递进 + 三维度并行

### 2.1 五层递进调研框架

任何"AI+行业"的深度调研都应遵循五层递进结构，确保调研既有历史纵深又有落地蓝图：

| 层级 | 名称 | 调研重点 | 关键问题 |
|------|------|---------|---------|
| **第一层** | 历史脉络层 | 该领域的发展史与演进阶段 | 这个领域经历了哪些阶段？每个阶段的核心模式是什么？ |
| **第二层** | 传统架构层 | 传统技术架构与核心设计机制 | 传统模式的核心架构是什么？有哪些经过验证的设计智慧？ |
| **第三层** | AI驱动层 | AI如何重塑该领域 | 有哪些代表性AI产品/平台？它们的技术架构是什么？ |
| **第四层** | 交互设计层 | 用户体验与设计模式 | 该领域的核心交互模式是什么？AI如何改变交互方式？ |
| **第五层** | 落地蓝图层 | 目标行业+AI的融合架构设计 | 如何将传统智慧与AI能力结合？具体的架构方案是什么？ |

**五层之间的关系**：前四层是"调研"，第五层是"综合"。前四层为第五层提供素材，第五层把素材转化为可执行的方案。没有前四层的纵深，第五层就是空中楼阁；没有第五层的综合，前四层就是信息堆砌。

### 2.2 三维度并行调研法

将"AI+行业"的大主题拆解为三个独立子维度，用子代理并行调研：

| 维度 | 覆盖范围 | 对应五层 |
|------|---------|---------|
| **维度A：历史与传统** | 发展史、传统模式、经典案例、设计哲学 | 第一层 + 第二层 |
| **维度B：AI新架构** | 代表性AI产品、技术架构、核心能力、认知模型 | 第三层 |
| **维度C：设计与落地** | 交互设计模式、行业适配、技术实现、架构蓝图 | 第四层 + 第五层 |

**并行执行原则**：
- 每个维度独立调研，不依赖其他维度的结果
- 每个维度进行多轮搜索（3-5轮），收集详细案例
- 每个维度的调研结果包含具体案例、设计机制、来源URL
- 三个维度的结果在"洞察整合"阶段交叉验证、综合提炼

**为什么不拆成更多维度**：三个维度是并行调研的最佳平衡点——足够覆盖主题的全貌，又不会因维度过多导致整合困难。超过三个维度时，维度间的交叉关系呈指数级增长，整合成本超过并行收益。

### 2.3 洞察整合：交叉发现

三个维度并行调研后，最有价值的洞察往往出现在维度交叉点：

| 交叉点 | 洞察类型 | 示例（AI+医疗） |
|--------|---------|----------------|
| A×B 历史×AI架构 | "传统模式的哪些设计被AI继承了？哪些被颠覆了？" | 传统PACS影像系统的分层架构被AI影像诊断继承，但诊断逻辑从规则匹配变为深度学习 |
| B×C AI架构×设计 | "AI的技术能力如何改变了交互方式？" | 大模型使自然语言问诊成为可能，替代了传统的表单式病历录入 |
| A×C 历史×设计 | "传统交互模式中哪些设计智慧值得保留？" | 望闻问切的四诊法可作为AI问诊的交互框架，让AI辅助而非替代医生判断 |
| A×B×C 三维交叉 | "传统智慧+AI能力+交互创新的最优融合点" | AI影像诊断保留PACS工作流 + 深度学习诊断 + 医生审核确认的"人机协同"模式 |

## 三、完整执行流程

### Phase 1：触发识别与主题确认

#### Step 1.1：识别调研需求信号

用户说出以下类型的话时，触发本流程：
- "帮我调研AI+XX领域的设计和架构"
- "深入调研XX领域的AI应用"
- "我要开发一个AI+XX的产品，给我参考"
- "调研XX领域，给我html格式的报告"

**检验标准**：如果用户的请求可以被转化为"对AI在某个领域的应用进行系统性深度调研，并输出结构化报告"，则进入本流程。

#### Step 1.2：确认目标领域与调研深度

与用户确认：
- **目标领域**：AI+什么行业？（如AI+医疗、AI+教育、AI+金融）
- **调研深度**：概览级（5-10段）| 标准级（20-40段）| 深度级（无上限）
- **输出格式**：HTML报告（默认）| Markdown | 其他

**输出**：确认的目标领域和调研规格。

---

### Phase 2：维度拆解

#### Step 2.1：将目标领域拆解为三个调研维度

基于目标领域的特征，将"AI+领域"拆解为三个独立子维度。

**拆解原则**：
- 三个维度覆盖"五层递进"的全部层级
- 每个维度可独立调研，不依赖其他维度
- 每个维度有明确的搜索关键词集合

**拆解模板**：

```
维度A：历史与传统
  → 该领域的发展史、传统技术/模式、经典案例、设计哲学
  → 搜索关键词："[领域]发展史"、"[领域]传统技术"、"[领域]经典案例"

维度B：AI新架构
  → 代表性AI产品/平台、技术架构、核心能力、认知模型
  → 搜索关键词："AI [领域] 产品"、"AI [领域] 技术架构"、"[领域] 大模型应用"

维度C：设计与落地
  → 交互设计模式、行业适配要点、技术实现方案、架构蓝图
  → 搜索关键词："AI [领域] 交互设计"、"AI [领域] 技术实现"、"[领域] AI架构设计"
```

**示例（AI+医疗）**：

| 维度 | 覆盖范围 | 搜索关键词示例 |
|------|---------|---------------|
| 维度A | 传统医学→现代医院→HIS/PACS/电子病历的发展史 | "医院信息系统发展史"、"PACS影像系统架构"、"电子病历演进" |
| 维度B | IBM Watson、DeepMind眼底诊断、AI影像诊断、医疗大模型 | "IBM Watson Health"、"AI医疗影像诊断"、"医疗大模型 2025" |
| 维度C | 医生工作站交互、患者端体验、AI辅助诊断架构、人机协同设计 | "AI医疗交互设计"、"医生工作站 UX"、"AI辅助诊断架构" |

**输出**：三个维度的调研规格（覆盖范围 + 搜索关键词）。

---

### Phase 3：并行调研

#### Step 3.1：启动三维度并行调研

为每个维度启动一个独立的调研子代理（Explore类型），并行执行。

**每个子代理的指令模板**：

```
请深入调研[维度描述]。需要覆盖以下方面：
[具体子主题列表]

请对每个主题进行多轮搜索（3-5轮），收集尽可能详细的信息。
返回时请按主题组织，包含具体案例、设计机制、技术架构的详细描述。
标注信息来源URL。
```

**并行约束**：
- 同时启动的子代理不超过3个
- 每个子代理独立搜索，不共享中间结果
- 每个子代理返回结构化的调研结果（按主题组织 + 来源URL）

**输出**：三个维度的调研结果（各自独立、结构化、带来源）。

#### Step 3.2：调研质量检查

对每个维度的调研结果进行质量检查：

| 检查项 | 标准 | 不达标处理 |
|--------|------|-----------|
| **覆盖度** | 是否覆盖了该维度的所有子主题 | 补充搜索遗漏的子主题 |
| **深度** | 是否有具体案例和机制描述，而非概述 | 针对浅层内容补充搜索 |
| **来源** | 是否标注了信息来源URL | 标注来源或标记为[未验证] |
| **交叉验证** | 核心声明是否有≥2个独立来源 | 标记为[单一来源] |

**输出**：通过质量检查的三个维度调研结果。

---

### Phase 4：洞察整合

#### Step 4.1：交叉分析

将三个维度的调研结果放在一起，进行交叉分析：

1. **继承与颠覆**：维度A的传统模式中，哪些设计被维度B的AI产品继承了？哪些被颠覆了？
2. **能力与交互**：维度B的AI技术能力，如何改变了维度C的交互设计？
3. **传统智慧保留**：维度A的传统交互模式中，哪些设计智慧值得在AI时代保留？
4. **最优融合点**：传统智慧+AI能力+交互创新的三维交叉点在哪里？

**输出**：4-6条交叉洞察（每条洞察指向一个可行动的设计决策）。

#### Step 4.2：提炼核心论点

基于交叉洞察，提炼报告的核心论点（1-3条）：

**核心论点公式**：
```
[目标领域]的AI化本质是"[传统模式的核心特征] + [AI的核心能力] + [交互创新]"的融合 —
用[传统智慧]保证[可靠性/连贯性]，用[AI能力]创造[新可能性]，用[交互设计]确保[可用性]。
```

**示例（AI+医疗）**：
> AI医疗的架构本质是"传统诊疗流程 + AI诊断能力 + 人机协同交互"的融合 — 用循证医学的诊疗规范保证医疗安全，用深度学习创造早期筛查的新可能，用人机协同交互确保医生的主导权。

**输出**：1-3条核心论点 + 4-6条交叉洞察。

### Phase 5：HTML报告生成

#### Step 5.1：报告结构设计

基于五层递进框架，设计报告的章节结构：

```
报告结构模板：
├── Hero（标题 + 副标题 + 元信息）
├── 目录（TOC）
├── 执行摘要（核心论点 + 关键发现 + 行动建议）
├── 第一章：历史脉络（对应第一层）
├── 第二章：传统架构与设计机制（对应第二层）
├── 第三章：传统领域的经典案例（对应第一层+第二层交叉）
├── 第四章：AI驱动的代表性产品（对应第三层）
├── 第五章：LLM/AI的技术架构（对应第三层深入）
├── 第六章：交互设计模式（对应第四层）
├── 第七章：核心亮点与吸引力分析（对应第四层提炼）
├── 第八章：目标领域+AI融合架构蓝图（对应第五层）
├── 第九章：技术实现方案（对应第五层落地）
├── 总结与行动建议
└── Sources（引用来源列表）
```

**章节数量适配**：概览级5-6章，标准级8-10章，深度级10-12章。

#### Step 5.2：视觉DNA注入（铁幕·Iron）

报告HTML遵循以下视觉规范：

| 维度 | 规范 | CSS实现 |
|------|------|---------|
| **配色** | 暗色基底 + 金色/翡翠双色调 | `--bg: #0d0e12; --accent: #c9a961; --accent2: #7b9b7e;` |
| **字体** | 衬线标题 + 无衬线正文 + 等宽代码 | CrimsonPro(标题) + InstrumentSans(正文) + IBMPlexMono(代码) |
| **零圆角倾向** | 直线设计为主，卡片用小圆角(6px) | `border-radius: 6px;` |
| **实色边框** | 用边框而非阴影建立层次 | `border: 1px solid var(--rule);` |
| **宽字距标题** | 标题字母间距增大 | `letter-spacing: 0.2em;` |
| **结构优于装饰** | 信息靠字号+对齐+边框，不靠渐变/浮动 | 章节用边框分隔，非阴影 |
| **表格优先** | 比较性数据用表格而非长文 | `<table>` + sticky header |

#### Step 5.3：引用规范

报告中所有事实性声明必须有引用来源：

**行内引用**（HTML格式）：
```html
<sup><a href="#cite-1">[1]</a></sup>
```

**来源列表**（footer）：
```html
<footer>
  <div class="sources">
    <h2>Sources</h2>
    <ol>
      <li id="cite-1">
        <span class="src-title">作者/机构，文档标题。简要描述。</span>
        <a class="src-url" href="https://example.com/source" target="_blank">https://example.com/source</a>
      </li>
    </ol>
  </div>
</footer>
```

**引用密度**：每个实质性声明1-3条引用；核心论点至少3个独立来源交叉验证。

#### Step 5.4：架构图生成

报告中至少包含1-3张架构图，使用Mermaid绘制：

```html
<pre class="mermaid">
flowchart TB
    subgraph 层A["层A名称"]
        A1["组件1"]
        A2["组件2"]
    end
    subgraph 层B["层B名称"]
        B1["组件1"]
    end
    层A --> 层B
</pre>
```

**图表类型选择**：
- 流程/架构 → `flowchart`
- 状态/决策 → `stateDiagram`
- 时序/交互 → `sequenceDiagram`
- 数据对比 → ECharts表格/柱状图

**输出**：完整的HTML报告文件（含字体、JS库、引用、架构图）。

## 四、HTML报告规范

### 4.1 必需组件清单

每份报告必须包含以下组件：

| 组件 | 必需性 | 说明 |
|------|--------|------|
| Hero封面 | 必需 | 标题 + 副标题 + 日期 + 元信息 |
| 目录(TOC) | 必需 | 可点击的章节导航 |
| 执行摘要 | 必需 | 核心论点 + 关键发现 + 行动建议 |
| 主体章节 | 必需 | 按五层递进框架组织 |
| 表格 | 必需 | 至少3张比较性表格 |
| 架构图 | 必需 | 至少1张Mermaid架构图 |
| Callout高亮框 | 推荐 | 标注关键洞察和设计建议 |
| 引用来源 | 必需 | 行内引用 + footer来源列表 |
| 页脚元信息 | 推荐 | 生成时间 + 报告标题 |

## 五、常见陷阱与避坑指南

| 陷阱 | 表现 | 后果 | 修正 |
|------|------|------|------|
| **信息堆砌陷阱** | 把搜索结果罗列成文档，没有洞察提炼 | 用户拿到后看不出"所以呢" | 每个章节必须有"对目标领域的启示"或"核心洞察" |
| **跳过历史调研** | 直接调研AI产品，不调研传统模式 | 重复造轮子，错过传统设计智慧 | 必须覆盖第一层+第二层，找到传统模式的经典设计 |
| **维度耦合** | 三个维度之间有依赖关系，无法真正并行 | 并行调研变成串行，效率无提升 | 拆解时确保每个维度可独立调研 |
| **搜索浅尝辄止** | 每个主题只搜1次就结束 | 信息不全面，错过关键案例 | 每个维度至少3-5轮搜索，追踪引用链 |
| **引用缺失** | 有事实声明但无来源 | 报告可信度存疑 | 所有事实性声明必须有行内引用 |
| **架构图缺失** | 全是文字描述，没有可视化 | 复杂架构难以理解 | 至少1张Mermaid架构图展示核心架构 |
| **无落地蓝图** | 调研结束但没有可执行的方案 | 报告只有"了解"价值，无"行动"价值 | 必须有第五层"落地蓝图"章节 |
| **视觉不一致** | 颜色/字体/间距随意 | 报告看起来不专业 | 严格遵循铁幕·Iron视觉DNA |
| **外部依赖** | 引用CDN字体/JS库 | 离线无法查看，分发困难 | 字体和JS库自托管在_shared/目录 |
| **AI万能论** | 认为AI可以替代传统模式的所有设计 | 架构方案脱离实际 | 强调"AI是增强不是替代"，保留传统智慧 |

## 七、执行原则

1. **历史纵深先于技术前瞻**：宁可多花时间调研传统模式的设计智慧，也不要只关注最新的AI产品。最有价值的洞察往往在"传统与AI的交叉点"。

2. **并行是效率的核心**：三个维度必须真正并行（同时启动子代理），而非伪并行（串行启动）。并行调研比线性调研效率高3倍。

3. **洞察先于信息**：调研结果不是"找到了什么"，而是"看懂了什么"。每个章节必须有洞察提炼，而非信息罗列。

4. **落地蓝图是终点**：调研的最终目的是"能做"。没有落地蓝图的调研报告是不完整的——它只回答了"是什么"，没回答"怎么做"。

5. **AI是增强不是替代**：始终问自己——传统模式中哪些设计智慧值得保留？AI如何增强而非替代这些设计？避免"AI万能论"。

6. **交叉验证是底线**：核心声明至少2个独立来源交叉验证。单一来源的声明必须标记[单一来源]。不编造引用。

7. **视觉是专业的表达**：遵循铁幕·Iron视觉DNA不是装饰偏好，是专业态度的体现。一份视觉混乱的报告，内容再好也难以被认真对待。

8. **自包含是分发的前提**：报告必须是零外部依赖的自包含文件。任何CDN依赖都会导致离线无法查看、分发后失效。

## 附录：AI+医疗调研示例

以下为使用本技能调研"AI+医疗"领域的示例拆解，演示方法论的完整应用。

### 示例：维度拆解

| 维度 | 覆盖范围 | 代表性案例 |
|------|---------|-----------|
| **维度A：历史与传统** | 传统医学→现代医院→HIS/PACS/电子病历 | 望闻问切四诊法、HIS医院信息系统、PACS影像存档系统、电子病历(EMR) |
| **维度B：AI新架构** | AI影像诊断、AI辅助诊疗、医疗大模型 | IBM Watson Health肿瘤系统、Google DeepMind眼底诊断、AI+PACS影像分析、医疗大模型 |
| **维度C：设计与落地** | 医生工作站交互、人机协同设计、AI医院架构 | 医生审核确认流程、AI辅助诊断的置信度展示、人机协同诊疗架构 |

### 示例：交叉洞察

| 交叉点 | 洞察 |
|--------|------|
| A×B | 传统PACS的分层架构被AI影像诊断继承，但诊断逻辑从规则匹配变为深度学习 |
| B×C | 大模型使自然语言问诊成为可能，替代了传统表单式病历录入 |
| A×C | 望闻问切四诊法可作为AI问诊的交互框架，让AI辅助而非替代医生判断 |
| A×B×C | AI影像诊断保留PACS工作流 + 深度学习诊断 + 医生审核确认的"人机协同"模式 |

### 示例：核心论点

> AI医疗的架构本质是"传统诊疗流程 + AI诊断能力 + 人机协同交互"的融合 — 用循证医学规范保证医疗安全，用深度学习创造早期筛查新可能，用人机协同交互确保医生主导权。
