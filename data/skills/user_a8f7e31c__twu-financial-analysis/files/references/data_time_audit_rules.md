# 数据时间审计通用规则（v1.0）

> 2026-07-29 info-digest 事故蒸馏。适用于所有涉及金融/时效/市场数据的 skill。
> 本规则作为 P0 约束注入，优先级高于其他输出规范。

---

## 核心原则

**本 skill 对时间高度敏感。所有涉及数值、市场数据、事件时间的断言，都必须经过数据时间审计。**

---

## 规则一：区分"来源时间"和"数据时间"

| 概念 | 定义 | 示例 |
|---|---|---|
| 来源时间 | 文章/报道的发布时间 | 2026-07-29 07:24 发布的新闻 |
| 数据时间 | 数据/事件实际发生的时间 | 文章中描述的是 7/28 的行情 |

**铁律**：不能因为来源时间是"今天"，就把文章内的数据当作"今天的数据"。必须通过阅读正文来确定数据时间。

---

## 规则二：不可能性检查（每步执行前强制）

获取当前时间后，对每条数值断言做以下检查：

**A股**：
- 交易日 09:30-11:30 / 13:00-15:00 → 可以有当日盘中数据
- 其他时间 → 只能用"昨日收盘"或"最近交易日收盘"
- **当前时间 < 09:30** → 当日任何"盘中""早盘""冲高回落"等表述均为编造

**港股**：
- 交易日 09:30-16:00 → 可以有当日盘中数据
- 其他时间 → 只能用"昨日收盘"

**美股**：
- 夏令时 21:30-04:00（北京时间）→ 可以有当日盘中数据
- 其他时间 → 标注"前日收盘"或"夜盘"

**商品/外汇**：
- 全球几乎24小时交易，但周末可能休市
- 仍需标注精确时间："X月X日XX时(XX市场)"

**新闻/事件类**：
- 正文明确写"今日""X月X日"发生了某事 → 可以引用
- 正文写"预计""展望""或将"（未来时）→ 归类为分析/预测，必须标注

---

## 规则三：输出格式规范

**所有数值断言必须附带精确时间戳**。格式：

```
[标的] [数值]（[时间标签]）
```

时间标签对照表：

| 场景 | 时间标签 | 示例 |
|---|---|---|
| A股/港股收盘数据 | {M}月{D}日收盘 | 上证 3813（7/28收盘） |
| A股/港股盘中（交易时段内） | {M}月{D}日盘中 | 上证 3830（7/29盘中） |
| 美股收盘 | {M}月{D}日收盘 | 道指 52747（7/28收盘） |
| 美股夜盘 | {M}月{D}日夜盘 | WTI 82.69（7/29亚盘） |
| 商品实时期货 | {M}月{D}日{HH}:{MM} | 布油 84.09（7/29 08:00） |
| 前一周末/节前最后一个交易日 | X月X日收盘（最近交易日） | — |
| 非当日数据但有价值 | X月X日（最新可得） | — |

---

## 规则四：歧义词汇禁列表

| 禁止 | 替换为 |
|---|---|
| "今日盘中"（未开盘时） | "X月X日收盘" |
| "今日早盘" | "X月X日收盘" 或删除（取决于上下文） |
| "今天""今日"（指行情时） | 具体日期 |
| "当前""目前"（指数据时） | 具体日期或"截至X月X日" |
| "最新"（指行情时） | 具体时间标签 |
| "最近""近期"（无锚定时） | "近N个交易日"/"自X月X日以来" |

---

## 规则五：分析/预测 vs 事实/数据的区分

| 类别 | 特征词 | 处理方式 |
|---|---|---|
| 事实 | "报收""收盘""发布""数据显示" | 可纳入"事实"层，标注数据时间 |
| 分析 | "预计""有望""或将""市场预期" | 降级为预期/观点，标注来源和发布时间 |
| 预测 | "目标价""看多""看空" | 归类为机构观点，明确标注机构和时间 |
| 混合 | 同一段落既有事实又有判断 | 分别标注。如"昨日收盘3813（事实），预计今日反弹（观点）" |

---

## 规则六：最终输出审计

HTML/报告生成前，执行一次扫尾检查：

1. 全文搜索歧义词汇（规则四中的禁列表）
2. 检查市场全景表的每一行，确认均有精确时间标签
3. 对"A股""港股"行情数据，核对当前时间是否处于该市场的交易时段
4. 所有"事实"类断言必须有可追溯的原文来源和时间戳
5. 不满足任意一条 → 不输出，退回精炼步骤修正

---

## 规则七：被纠正后的处理流程

如果用户指出时间数据错误（无论大小），按以下步骤执行：

1. 确认具体错误：哪条数据、什么问题
2. 追溯错因：是"把预测当事实"还是"没做不可能性检查"还是"时间标签缺失"
3. 补入规则：将此次错误对应的防护措施追加到本文件的对应规则中
4. 全量扫荡：检查本轮其他输出中是否还有同类型错误（不限于出错的 skill）
5. 汇报：向用户说明修正了什么、追加了什么规则
